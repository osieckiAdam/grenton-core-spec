# Grenton Core — conformance suite contract

| | |
|---|---|
| **Suite version** | 0.15.0 (specification 0.15.0, case schema 1) |
| **Applies to** | `spec/grenton-core-design.md` §9 |

The conformance suite is **data, not code**: every case is a JSON file in `conformance/cases/`. The port supplies a thin runner that loads the cases, calls the port's production API and compares the observation with the expectation. Adding a case once covers all ports.

## 1. Profiles

Conformance is declared **per profile** — passing part of the suite is not "full conformance".

| Profile | Scope | Since suite version |
|---|---|---|
| `stateless` | stateless functions: AES, frames, payloads, casting, URL/PIN, coercions, number format | 0.1.0 |
| `mapping` | `data.json` → devices/entities, skipped widgets | 0.2.0 (0.3.0: thermostat, `SCENE_DOUBLE`, `HEADER`; 0.4.0: `page`, physical objects) |
| `provisioning` | Object Manager responses over HTTP and interface archives → interface or error (§4.2–§4.3) | 0.15.0 |
| `session` | conversation scenarios of a single CLU session (§5.4) with a scenario-driven CLU and virtual time | 0.5.0 |
| `project` | interface import from a `.omp` project file (§4.5) → the same interface and the same devices as from OM | 0.8.0 |
| `entities` | bound entities over a filled state store: normalized reads and the actions every intent sends (§6.1–§6.3) | 0.15.0 |

## 2. Case file

```json
{
  "schemaVersion": 1,
  "id": "value.cast.int64-max",
  "specRefs": ["model.cast"],
  "description": "…",
  "provenance": "spec §3.1 + §9.2",
  "operation": "value.cast",
  "input": { "text": "9223372036854775807" },
  "expect": { "outcome": "ok", "value": { "value": { "type": "int", "value": "9223372036854775807" } } }
}
```

- `id` — stable, globally unique, equal to the file name; starts with the operation group.
- `specRefs` — stable requirement ids (table §6, machine-readable in `manifest.json` → `requirements`), not section numbers — renumbering the specification does not invalidate cases.
- `provenance` — where the expected result comes from. **Expectations are never generated by the port under test**; sources: the literal text of the specification, `openssl`, the semantics of the reference implementation (Python).
- `expect` — exactly one of:
  - `{"outcome": "ok", "value": …}` — the operation succeeded, `value` is the projection of the result,
  - `{"outcome": "error", "code": "…"}` — the operation raised an error from the §8 taxonomy (`crypto.invalidKeyMaterial`, `provisioning.authenticationFailed`, `provisioning.connection`, `provisioning.invalidData`, `payload.unresolvedPlaceholder`, …),
  - `{"outcome": "reject"}` — the input was rejected without an error (the parser returns "no result", reception silently drops the datagram).

Schema: `conformance/schemas/case.schema.json` (JSON Schema 2020-12). Unknown fields are an error.

## 3. Values

`GrentonValue` is encoded as a tagged value:

| Type | Encoding | Notes |
|---|---|---|
| null | `{"type":"null"}` | |
| bool | `{"type":"bool","value":true}` | |
| int | `{"type":"int","value":"42"}` | **decimal string** — Int64 does not fit in JS numbers |
| double | `{"type":"double","bits":"4035800000000000","decimal":"21.5"}` | the **binary64 bits** are compared; `decimal` is informational and the runner ignores it |
| string | `{"type":"string","value":"ON"}` | |

Comparison of `ok.value`: structural JSON equality, object key order is irrelevant; arrays are compared positionally. Resulting strings (payloads, URLs, number format) are compared byte for byte.

## 4a. Mapping projection

`ok.value` of the `mapping.interface` operation:

```json
{
  "devices": [
    { "id": "w-onoff", "widgetType": "ON_OFF", "kind": "switch", "name": "Lampa / Kinkiet", "icon": null,
      "page": { "index": 0, "name": "Salon", "icon": "home" }, "section": { "id": "h-1", "title": "Oświetlenie" },
      "entities": [ { "kind": "switch", "id": "w-onoff_0", "name": "Lampa", "icon": "bulb", "state": { … }, "onAction": { … }, … } ] }
  ],
  "physicalObjects": [
    { "key": { "cluId": "CLU_1", "kind": "object", "name": "DOU8272", "index": "0" },
      "widgets": [ { "deviceId": "w-onoff", "widgetType": "ON_OFF", "name": "Lampa / Kinkiet",
                     "page": { "index": 0, "name": "Salon" }, "entityIds": ["w-onoff_0"] } ] }
  ],
  "skippedWidgets": [ ["FANCY_NEW_WIDGET", null], [] ]
}
```

- `devices` — in normative order (spec §6.1); compared positionally, including devices without entities.
- `physicalObjects` — the grouping of §6.6, in order of first use; compared positionally.
- `icon` — the widget's icon name or `null`; `page.icon` — the page's; every entity's `icon` — its component's `image`/`icon`, else the widget's, else `null` (§6.1).
- `section` — `{id, title}` of the device's section header (§6.1), or `null`.
- `skippedWidgets` — one list per page: the `type` of the skipped widgets in order (`null` when there is no `type`). The text of the reason is not compared — error messages are language-specific.
- `ValueRef`: `{"callType":"VARIABLE","cluId","index"}` or `{"callType":"ATTRIBUTE","cluId","objectName","index"}` (a variable's `objectName` is logically ignored, §3.2).
- `ActionRef`: `{"callType","cluId","objectName","event","value"}` + `index` for variants other than `SCRIPT`.
- Numbers from `data.json` (`min`, `max`, `precision`, `range`) — plain JSON numbers: they come from JSON, so they parse identically in every language.
- Entity fields by `kind`:

| Entity `kind` | Fields (besides `kind`, `id`, `name`, `icon`) |
|---|---|
| `switch` | `state`, `onAction`, `offAction`, `onIndication`, `offIndication` |
| `dimmableLight` | `state`, `min`, `max`, `precision`, `onAction`, `offAction`, `setValueAction` |
| `hsbLight` | `powerState`, `onAction`, `offAction`, `hue` / `saturation` / `brightness`: `{state, setAction, range:{min,max}}` |
| `contactSensor` | `state`, `reversed`, `onIndication`, `offIndication` |
| `sensor` | `state`, `sensorKind`, `unit` (canonical or `null`), `grentonUnit`, `valueType`, `precision` (`null` when absent) |
| `numberSetting` | `state`, `setValueAction`, `min`, `max`, `precision` |
| `cover` | `motionState`, `position`, `setPositionAction`, `tilt` (`{position, setAction}` or `null`), `stopAction` (or `null`) |
| `stateSensor` | `state` |
| `trigger`, `sceneTrigger` | `action` |
| `camera` | `streamUrl` |
| `thermostat` | `currentTemperature`, `targetTemperature`, `setTargetTemperatureAction`, `minTemperature`, `maxTemperature`, `output` (`null` when absent), `mode` / `power` (`{state, setAction}` or `null`) |
| `eventSchedule` | `state`, `ruleList`, `addRuleAction`, `deleteRuleAction`, and `ruleCount`, `ruleSpace`, `nextRule`, `currentRule`, `startAction`, `stopAction`, `enableRuleAction`, `disableRuleAction` (`null` when absent) |
| `tvRemote` | `buttons` — an object of button name → `ActionRef`, only the buttons present (an empty object for a remote without buttons) |

**Fixtures** live in `conformance/fixtures/` and are listed in the manifest with a SHA-256 checksum (the runner verifies them just like cases). A widget that **must** be skipped because of a missing field or an unknown enum is marked in the fixture with the field `"x-conformance-expect-skip": true`. Ports ignore it (unknown fields, §3.6 item 4); only the oracle `tools/oracles/mapping.py` reads it, because §3.5 does not give the full field schema of every widget.

## 4b. Session scenarios (`session` profile)

The `session.scenario` operation checks a single CLU session (spec §5.3–§5.4) in a conversation with a CLU whose role is played by the runner, step by step according to the scenario. Input: `{"clu": {"id", "ip", "port"}, "responseTimeoutMs", "pingIntervalMs"?, "registerIntervalMs"?, "registerFrameLimitBytes"?, "steps": [...]}`. An omitted interval means the port's default interval (spec §5.4.4: 5 s and 30 s) — this is how the loop scenarios check the normative values; the remaining scenarios push the loops out by an hour so that they do not interleave with the steps. `registerFrameLimitBytes` is the register frame limit (spec §5.4.2 item 1); omitted, it means the default 1471 B — this is how the `default-frame-limit-*` scenarios check it. The remaining multi-chunk scenarios give a smaller limit so that the key list stays short. The `ok` result is `{"completed": true}`. A runner that encounters a non-matching step returns `{"completed": false, "failedStep": <index>, "observed": …}`, so that the difference points to the step.

**What the port exposes to the runner** (names are arbitrary, behavior per §5.4): creating a session for a CLU with the key and IV from §9.1, a clock and a transport supplied by the runner, and an optional register frame limit; `start()`, `stop()`, `ping()`, `register(keys) → slots`, `execute(action)`, the current state (§5.4.5) and the report stream (§5.4.3). The runner's transport sees every opened socket, every sent datagram and every socket close; the runner decrypts the sent datagrams and encrypts the injected ones, so scenarios operate on frame text (§5.2).

**Virtual time.** The session clock belongs to the runner and stands still until an `advance` step moves it. The response timeout (§5.4.1) and the loop intervals (§5.4.4) elapse solely through `advance`. `advance` moves the clock in a single jump; the scenario chooses its steps so that at most one deadline of each timer elapses within one `advance`, and so that deadlines of different timers do not fall at the same instant, because their order is unspecified.

**Barrier.** After every step the runner waits until the session stops performing work that is possible without time and without new datagrams (in practice: until the scheduled tasks have run), including the delivery of reports to the stream, which the runner subscribes to before the first step. Only then does it check the expectations. `expectSent` waits for a datagram for at most a runner-chosen amount of real time.

**End of scenario.** After the last step, before the runner itself stops the session, an implicit `expectQuiet` and `expectNoReport` apply: a sent datagram or a delivered report that no step checked makes the run fail (`failedStep` equal to the number of steps). A scenario that ends with registered chunks does not have to check the `clientDestroy` of the stop — it is sent only by the runner's stop, after this check.

**Negative assertions.** `expectQuiet` and `expectNoReport` assert the absence of an event, so after the barrier the runner additionally observes a **quiet window: at least 200 ms of real time**, and only then considers the absence confirmed. This is a probabilistic guarantee: a port that delays work for longer than the window without involving the session clock may pass it. A runner whose environment allows idleness to be detected deterministically (its own executor, explicit draining of queues) may do that instead of the window.

**Capturing.** A `msgId` of the form `$name` binds to the observed value on first use, and on subsequent uses must equal it. Sockets are named with `@name` labels: the first use binds the label to a socket **different from all those already named**, subsequent uses must point to the same socket. The session uses a single socket (§5.4), so scenarios name it `@main`, and after a repeated `start()` the new socket gets a new label.

Steps (every object has exactly one verb):

| Step | Meaning |
|---|---|
| `{"call": "start" \| "stop" \| "ping", "as": "x"}` | starts a session operation in the background; `await` receives the result |
| `{"call": "register" \| "fetch", "keys": [ValueRef…], "as": "x"}` | as above; `keys` in the `payload.register` format; both split the keys by the `registerFrameLimitBytes` limit (§5.4.2), `fetch` with the `fetchValues` frame text |
| `{"call": "execute", "action": {ActionRef as in data.json}, "as": "x"}` | as above |
| `{"await": "x", "result": …}` | waits for operation `x` to finish and compares the result: `null` (start/stop), `{"ok": true\|false}` (ping), `{"slots": [tagged value \| {"failed": true}]}` (register, fetch), `{"ok": true}` or `{"error": code}` (execute) |
| `{"expectSent": {"socket": "@s", "msgId": "$m" \| "…", "payload": "…"}}` | the next sent datagram is `req::{msgId}:{payload}` from socket `@s` |
| `{"expectQuiet": true}` | after the barrier nothing was sent beyond what was already checked |
| `{"respond": {"socket": "@s", "msgId": "$m" \| "…", "payload": "…", "upper": bool?}}` | the CLU responds on socket `@s` with the frame `resp:{clu.ip}:{msgId}:{payload}` (`upper`: `msgId` in uppercase) |
| `{"deliver": {"socket": "@s", "frame": "…", "encrypted": bool}}` | an arbitrary frame on the socket; `encrypted: false` sends bytes that cannot be decrypted |
| `{"advance": ms}` | moves the virtual clock by `ms` > 0 |
| `{"expectState": "idle" \| "starting" \| "ready" \| "degraded" \| "stopped"}` | the current session state |
| `{"expectReport": {"keys": [ValueRef…], "values": [tagged value \| {"failed": true}]}}` | the next report from the report stream |
| `{"expectNoReport": true}` | no new report after the barrier |
| `{"expectClosed": "@s"}` | socket `@s` was closed by the session |
| `{"fail": "@s"}` | the transport reports a failure of socket `@s`: reception on it ends (§5.4.1 item 4) |

The structure of the steps is described by `conformance/schemas/case.schema.json`, and `tools/suite.py check` checks every case against the schema and the rules between steps (labels and captures bound before use, every `call` received by an `await`). The runner rejects a step it does not recognize instead of skipping it.

`execute` error codes: `session.timeout` (§5.4.1 item 3), `session.notConnected` (§5.4.5, no main socket), `session.connectionClosed` (§5.4.1 item 4, §5.4.5), `payload.unresolvedPlaceholder` (§3.3).

## 4c. Project file import (`project` profile)

| Operation | Input | `ok.value` | Other outcomes |
|---|---|---|---|
| `provisioning.omp` | `fixture` — path of a `.omp` file relative to `conformance/`; `interfaceId`? | `interfaces[]`, `interface`, `mapping` | `error provisioning.invalidData`, `error provisioning.interfaceNotFound`, `error provisioning.interfaceAmbiguous` (§4.5) |

The port imports the file (§4.5) and projects the result:

- `interfaces` — the list of `{id, name}` of all interfaces in the archive, in the order of the `nodes/{n}/data.json` entries in the archive (§4.5.2);
- `interface` — the root of the selected interface: `id`, `version`, `name`, `icon`, `theme`, `encryption: {key, iv}`, `clus[]` (fields of §3.4 in the order of §4.5.4), `pushNotifications[]` and `pages[]` as `{name, icon, isFullscreenWidget, widgets: [{id, type}]}` — `widgets` are the widgets that passed the parsing of §3.6, in page order;
- `mapping` — the result of the `mapping.interface` operation (§4a) for the imported interface.

Widgets are thus checked by the mapping projection: import from `.omp` yields the same devices, entities and skips as the same interface fetched from OM. For widgets that Core does not map to devices (`HEADER`, `EVENT_SCHEDULER`), only their presence in `widgets` or in `skippedWidgets` matters; presentation fields, e.g. the `background` of scenes, are not checked by the projection.

**Fixtures** `.omp` live in `conformance/fixtures/projects/`; each of them (except `not-a-zip.omp`) is built by `python3 tools/suite.py fixtures` from readable sources in `conformance/sources/projects/{name}/` (`properties.xml`, `system.xml`, `nodes/*/data.json`); an optional `ORDER` file gives the order of the archive entries (without it — alphabetical) and does not itself end up in the archive. `check` compares the names, order and contents of the entries with the sources (not the bytes, because zlib varies) and checks that the transformed widgets have `unit` and `valueType` from §3.5. The oracle approximates the parsing of §3.6 with the rules the specification gives (§3.2, §3.3 and the field types of §3.5) — a widget that does not satisfy them is treated as skipped; §3.5 is not a full schema, so fixtures must not rely on anything beyond these rules. The oracle `tools/oracles/omp.py` is written from §4.5; it computes the expectations together with the mapping oracle.

## 4d. Object Manager responses and archives (`provisioning` profile)

| Operation | Input | `ok.value` | Other outcomes |
|---|---|---|---|
| `provisioning.archive` | `fixture` — path of a ZIP file relative to `conformance/` | `interface`, `mapping` | `error provisioning.invalidData` (§4.3) |
| `provisioning.fetch` | `pin`; `response` or `unreachable: true` | `requestTarget`, `interface`, `mapping` | `error provisioning.authenticationFailed`, `error provisioning.connection`, `error provisioning.invalidData` (§4.2–§4.3) |

`interface` and `mapping` are projected as in §4c.

**`provisioning.archive`** — the port reads an interface archive it already holds (a saved download), with the rules and limits of §4.3.

**`provisioning.fetch`** — the runner serves the response over **real HTTP**: it starts an HTTP/1.1 server on `127.0.0.1`, on a port the system chooses, and calls the port's production download with host `127.0.0.1`, that port and `pin`. The server answers **every** request with `response`:

- `status` — the status code;
- `headers`? — extra response headers, an object of name → value (e.g. `{"Location": "…"}`);
- `body`? — `{"fixture": path}` (the bytes of a file under `conformance/`) or `{"zeros": n}` (`n` zero bytes); without it the body is empty. The body is sent with `Content-Length`, and the server closes the connection after it.

`unreachable: true` replaces `response`: the runner passes a port on which nothing listens (it binds a TCP port and closes it), so the connection is refused.

The runner checks, besides the outcome:

- the server received **at most one request** — more means a redirect was followed or the request repeated (§4.2), and the case fails;
- `ok.value.requestTarget` — the request-target of that request exactly as received (`/api/v1/interface/hash/149853`);
- for an `error` outcome: **no text of the error contains the PIN** (§4.2) — every description the language gives the error value (its message, description and debug form) is searched for each non-empty form: `pin` as given, with every `White_Space` character removed, and that form percent-encoded as in §4.1. A match fails the case, as an observation.

**Fixtures** — the archives live in `conformance/fixtures/archives/`; each of them is built by `python3 tools/suite.py fixtures` from its recipe `conformance/sources/archives/{name}.json` — `raw` (the file is that text, not a ZIP) or `entries`: the entries in order, each with `name`, its content (`from` — a file under `conformance/`, or `text`), optional `padTo` (the content followed by spaces up to that many bytes; JSON allows trailing whitespace), `method` (`deflate`, the default, or `store`), and `lie` (`{"size": ±n}` changes the uncompressed size both headers declare, `{"crc": true}` breaks the CRC-32 in both). `check` re-reads every archive from its headers and verifies it against the recipe.

## 4e. Bound entities (`entities` profile)

| Operation | Input | `ok.value` | Other outcomes |
|---|---|---|---|
| `entity.read` | `fixture` (a `data.json` as in `mapping.interface`), `entityId`, `values` | `state` | |
| `entity.intent` | `fixture`, `entityId`, `values`, `intent`, `args`? | `actions` | `reject` (the entity refused the input; nothing is sent) |

The port maps the interface (§6.1 stage 1) and binds its entities (stage 2) to a state store the runner fills and to a **command sink** in place of the CLU sessions: the sink records every `ActionRef` the entity asks to execute, in order, and succeeds. Before the operation the runner writes `values` into the store; a key not listed has never been reported (unknown).

- `values` — a list of `{key, value}`: `key` a `ValueRef` as in the mapping projection (§4a), `value` a tagged value (§3).
- `entityId` — the id of one entity (§6.1); an id the mapping does not produce fails the case.

**`entity.read`** — `state` holds the entity's normalized state, one field per row of the table below. Booleans are JSON booleans, numbers are tagged values (§3) of the type given, enumerations are strings, and an unknown value is `null`.

| Entity `kind` | `state` fields |
|---|---|
| `switch` | `isOn` |
| `dimmableLight` | `isOn`, `brightness` (double) |
| `hsbLight` | `isOn`, `hue`, `saturation`, `brightness` (double) |
| `contactSensor` | `isActive` |
| `sensor` | `value` — the stored value as it is (a tagged value; `null` when never reported) |
| `numberSetting` | `value` (double) |
| `cover` | `position` (int), `isClosed`, `motion` (`idle` \| `opening` \| `closing` \| `unknown`), `tilt` (int; `null` without slats) |
| `stateSensor` | `state` (`stopped` \| `opening` \| `closing` \| `locked` \| `unknown`) |
| `thermostat` | `currentTemperature`, `targetTemperature`, `minTemperature`, `maxTemperature`, `output` (double), `mode` (`manual` \| `holiday` \| `schedule`), `isOn` |
| `eventSchedule` | `isActive`, `rules` (as in `schedule.rules`), `ruleCount`, `freeRuleSlots` (int), `nextRule`, `currentRule` (one rule as in `schedule.rules`, or `null`) |

The other kinds have no state; their cases are intents.

**`entity.intent`** — `actions` lists the `ActionRef`s the sink received, in order, projected as in §4a with the `value` the entity set; an empty list is a no-op. The intents (reference names, §2; `args` is an object, numbers are JSON numbers):

| Entity `kind` | `intent` and `args` |
|---|---|
| `switch` | `turnOn`, `turnOff` |
| `dimmableLight` | `turnOn`, `turnOff`, `setBrightness {brightness}` |
| `hsbLight` | `turnOn`, `turnOff`, `setColor {hue, saturation}`, `setBrightness {brightness}` |
| `numberSetting` | `setValue {value}` |
| `cover` | `open`, `close`, `stop`, `openTilt`, `closeTilt`, `setPosition {position}`, `setTilt {tilt}` (integers) |
| `trigger` | `press` |
| `sceneTrigger` | `run`, `run {parameter}` |
| `thermostat` | `setTargetTemperature {temperature}`, `setMode {mode}` (`manual` \| `holiday` \| `schedule`), `turnOn`, `turnOff` |
| `eventSchedule` | `setActive {active}`, `addRule {hour, minute, days}` (weekdays 0–6, 0 = Sunday), `deleteRule {id}`, `enableRule {id}`, `disableRule {id}` |
| `tvRemote` | `press {button}` |

`reject` means the entity refused the input as §6.3 prescribes (e.g. `addRule` with hour 24) and the sink received nothing; the runner checks both. The oracle `tools/oracles/entities.py` is written from §6.1–§6.3 and computes every `entity.*` expectation from the mapping oracle's entities; `check` also runs its schedule parser against the `schedule.rules` and `schedule.cron` cases.

## 5. Runner duties

The runner **fails closed**. A run is failed if:

1. the suite is missing (e.g. an uninitialized submodule) — an explicit message, not "0 tests",
2. `manifest.json` does not match the files (a missing/extra case or fixture, a wrong SHA-256 checksum),
3. a case has an unknown operation, an unsupported `schemaVersion`, cannot be decoded or does not satisfy the shape of §2 (extra or missing fields, empty `specRefs` or a requirement id outside `manifest.json` → `requirements`, a wrong shape of `expect`, an `id` different from the file name or a file outside `cases/`),
3a. the declaration of the port lists a profile the manifest does not know; the runner executes all cases of the declared profiles and reports the cases of the remaining profiles as not covered by the declaration (not as a success),
4. the declaration of the port points to a skip of a non-existent case or a skipped case **passes** (unexpected success — remove the skip),
5. the suite version in the declaration of the port ≠ `suiteVersion` from the manifest.

The runner calls only the production API and serializes the observation. It **must not** implement casting, mapping, PIN normalization or error decisions. Report per case: `id`, expectation, observation, the first differing JSON path.

### Declaration of the port

```json
{
  "suiteVersion": "<suiteVersion from manifest.json>",
  "profiles": ["stateless"],
  "skips": [{ "id": "…", "reason": "…", "issue": "…" }]
}
```

A port with a non-empty `skips` list declares conformance to the profile with exceptions — and must list them.

## 5a. Distribution

The suite is versioned together with the specification in the `grenton-core-spec` repo. Ports pin a specific commit (git submodule) or import a snapshot with a checksum. A correction of an expected result or a new case = a new suite version, even without a change to the specification.

## 7. Maintenance

```sh
python3 tools/suite.py check      # case validation + independent oracles (openssl, Python round)
python3 tools/suite.py manifest   # rebuild the manifest after adding/changing a case
python3 tools/suite.py fixtures   # rebuild the .omp fixtures (conformance/sources/projects/) and the archives (conformance/sources/archives/)
```

`check` recomputes the expectations wherever an independent oracle exists: ciphertexts via `openssl`, `number.format` via Python's `round()`, coercions via the expressions of the reference implementation (`value == "ON" or value == True`, `bool(value)`), `mapping.interface` via `tools/oracles/mapping.py` (written from the specification, not from the port), `provisioning.archive` and `provisioning.fetch` via `tools/oracles/archive.py` (§4.1–§4.3; it inflates and counts itself, because Python's `zipfile` trusts the declared sizes), `entity.*` via `tools/oracles/entities.py` (§6.1–§6.3, on top of the mapping oracle; its schedule parser is also run against the hand-written `schedule.*` cases), and every `decimal`/`bits` pair via the Python parser. It rejects an `entity.*` value under a key the entity does not read (it would silently test "unknown"), re-reads every archive's headers and inflated entries and compares them with its recipe, and reports fixtures that no case uses.

## 8. Out of scope — open decisions

- **`msg_id` validation:** §5.2 says "8 hex characters", but reception does not enforce it. The suite does not test malformed `msg_id` until the specification decides: strict or liberal.
- **The whitespace set for casting and report parsing:** the cases use only space and tab; the exact set is to be determined.
- **Position of a skipped widget** (e.g. `/pages/0/widgets/3`) — for now only the types per page are compared.
- **The response body limit** (§4.3 item 4) has no case: a body over 10 MiB that is still a readable archive cannot be built portably, and any other over-limit body fails as `invalidData` anyway. The `data.json` limit is tested exactly, at the limit and one byte over.
- **Logs** — §4.2 keeps the PIN out of logs too; the runner checks only the error texts, a port tests its log lines itself.
